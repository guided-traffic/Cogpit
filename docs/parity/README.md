# Parity and progress documents

> **Last reviewed:** 2026-10-12 · **Last updated:** 2026-10-16 · **Change:** minor (parity-checklist.md generated by hack/parity since 2026-10-16, refused when stale under make parity); minor (`make parity` checks the rows and counts the numbers; the counting rules) · **Target:** Lens Desktop 2026.10.51501

Cogpit is a clean-room reimplementation of the Kubernetes IDE Lens. These pages answer two
questions and nothing else: **how close are we to Lens**, and **what is left to do**. The method is
taken from [PhotoCraft](https://github.com/storytold/photocraft) (a Photoshop reimplementation in
Rust), whose progress docs follow the same structure.

Two generated pages exist in PhotoCraft and are part of this method. `parity-checklist.md` (every
row of the checklists, live or missing, with the counts) is generated here since 2026-10-16 by
[`hack/parity`](../../hack/parity/checklist.go): a plain `go run ./hack/parity` writes it when it
differs, and `make parity` (CI, `-check`) refuses a page that no longer matches the checklists, so a
change of a row's status or first cell commits the regenerated page with it. `scorecard.md` (from
`make scorecard`, measured checklists and performance and API-load budgets) has no generator yet.
The checklists in the hand-written pages are the only source; since 2026-10-12
[`make parity`](#make-parity) checks them and counts what they report
([D-15](../developer/decisions.md#d-15-progress-generators)). The generated pages are part of
milestone M0 in [`roadmap.md`](roadmap.md).

## Rules for every progress page

1. **Status line.** Each page starts with one quoted line: `Last reviewed` (someone checked the
   page against the code), `Last updated` (the content changed), `Change` (`major`, `minor` or
   `trivial`, with a few words on what changed) and `Target` (the Lens version measured against).
2. **Status vocabulary.** A checklist row is **done** (behaves as in Lens, and a test proves it),
   **partial** (exists, but differs from Lens or is untested) or **missing**. "Exists" is not
   "done": a row without a test is partial at best.
3. **Evidence.** Every non-missing row names its evidence: a file and line, a test name, a
   scorecard id or an issue number. A row without evidence is missing.
4. **Sources.** A row about Lens comes from Lens Desktop's documentation or release notes, or from
   a capture of the running Lens Desktop, never from OpenLens or Freelens
   ([D-12](../developer/decisions.md#d-12-parity-sources)). What the documentation leaves open is
   marked *capture needed*.
5. **Measured or estimated.** Every number says which it is. A measured number names how it was
   measured, so the next person can repeat it. Move an estimate only with new evidence.
6. **Hours.** Estimates are agent-hours: one Opus 5.5 agent working sequentially, including tests.
   Cogpit has no history to calibrate against yet; until it has, estimates use PhotoCraft's
   calibration (2–9 h per checklist item of UI or tool depth, 8–20 h per subsystem, from its 1,004
   merged PRs) and say so. Replace the borrowed calibration with Cogpit's own once ~100 PRs have
   merged.
7. **Revision history.** Each page ends with a table of dated changes. Add a row whenever the
   status line's `Last updated` moves.
8. **Same change.** Work that moves a number or closes a gap updates, in the same pull request,
   the checklist row, the gap entry in [`gaps.md`](gaps.md), the number in
   [`target-app-parity.md`](target-app-parity.md) and, when a headline moves,
   [`ROADMAP.md`](../../ROADMAP.md).
9. **Stable headings.** Numbers go in the text under a heading, never in the heading itself, so
   links to a section survive every re-measurement.

## make parity

`make parity` ([`hack/parity`](../../hack/parity/main.go)) reads `ROADMAP.md` and the pages
above, and runs in CI after the lint ([releasing › CI](../developer/releasing.md#ci)). It
refuses:

- **a row that appears twice:** two rows of one section with the same first cell (links read as
  their text, code marks and case ignored); in a revision history or a progress log, two
  identical rows;
- **a status it cannot read:** a checklist row's Status cell starts with `done`, `partial`,
  `missing`, `not a target` or `–` (nothing to build);
- **a row marked done or partial without evidence** in its Status or Evidence cell: a link to a
  code file or a picture (a link to another page of documentation is not evidence), a test name
  in backticks, or an issue (`#12`) ([rule 3](#rules-for-every-progress-page));
- **a reference that does not resolve:** a link on a progress page to a file that does not exist,
  a test named in a checklist that no `_test.go` file declares;
- **a command id the registry does not know** in a checklist's status or evidence. The first
  column, Actions and MCP tool name the target and may name a planned id; anywhere else an id is
  a claim about the code;
- **a generated page that differs** from what the checklists give (`parity-checklist.md`, under
  `-check`, as `make parity` runs it; a plain run writes the page instead);
- **a reported number that differs from the count:** the Feature breadth and Beyond Lens rows of
  `ROADMAP.md`, the headline and the breadth table of [`target-app-parity.md`](target-app-parity.md)
  (fractions, percentages and the weighted sum), and the Summary paragraphs of the four
  checklists. Keep those sentences' form ("55 of 64 resource views exist"): a reworded one fails
  until [`claims.go`](../../hack/parity/claims.go) learns it.

While a recount is due (agents working in parallel move rows, the lead recounts after the merge),
`make parity PARITY_FLAGS=-rows` checks the rows and leaves the reported numbers alone.

### How make parity counts

A row **exists** when it is done or partial. Rows marked `not a target` or `–` count in no
denominator.

| Component | Rows counted |
|---|---|
| Resource views | the rows of [`resource-parity.md`](resource-parity.md)'s view tables (first column "View") outside Paid Lens Desktop views; a row is one view, or the number its first cell gives as "(N views" (the Gateway API rows) |
| Resource actions | the distinct command ids in those tables' Actions columns and in the first column of Every kind, except an id followed by "not a target" before the next comma; an action exists when the registry has its id |
| Interface rows | the rows of [`ui-parity.md`](ui-parity.md) by their Plan column, `free` or `paid`; every table there has one. The free denominator is 121 (2026-10-12); the 123 that the third run could not reproduce counted the two paid shortcuts, whose table had no Plan column then |
| Packages, authentication | the rows of [`platform-parity.md`](platform-parity.md)'s two sections; a row whose first cell says "(paid)" belongs to another gap and does not count |
| Beyond Lens | every row of [`beyond-lens.md`](beyond-lens.md); not part of breadth |
| Weighted breadth | each component's fraction times its weight in the breadth table; the paid features' row comes from Lens's premium list, not a checklist, and is taken as written |

## Stages

| Stage | Meaning |
|---|---|
| **pre-alpha** | The [alpha gate](roadmap.md#alpha-gate) fails: at least one core workflow does not complete end to end |
| **alpha** | Every core workflow completes end to end on macOS; ready for real work is in the ~40–75% band |
| **beta** | Ready for real work ≥ ~75%, and no gap marked *blocks beta* in [`gaps.md`](gaps.md) |
| **1.0** | Ready for real work ≥ ~95% for the mainstream audience on macOS, Windows and Linux, signed releases with one-click updates |

## The two headline numbers

- **Feature breadth:** does each Lens feature exist in some form? Partly measurable (resource
  views, actions, menu items, shortcuts, preferences), weighted in
  [`target-app-parity.md`](target-app-parity.md#feature-breadth).
- **Ready for real work:** could someone who uses Lens every day switch to Cogpit? Estimated,
  weighted by dimension, with evidence per row. This is the number that decides the stage.

Breadth always runs ahead of readiness. PhotoCraft learnt this the expensive way: its menu
breadth reached 100% while readiness was ~45%, and its first users found broken basics that all
counted as "live" in the menu checklist. Never quote breadth as progress on its own.
